现在的 AI 已经可以完成相当复杂的编码任务。

真正让我开始重新设计开发流程的原因，并不是它“不会写代码”。很多时候，模型写得很快，调用链也能看懂，测试也会补，甚至能主动发现周边问题。

麻烦出现在另一层：**当 AI 拥有越来越大的执行能力以后，什么信息允许它自行推断，什么决定必须由人确认，什么时候可以直接改代码，什么时候应该停止执行并回到调查阶段？**

如果这些边界只存在于人的脑子里，那么模型每次接手任务时都要重新猜一遍。

一次猜对不难。连续经历调查、讨论、规划、编码、测试，再换几个不同上下文以后仍然保持同一个目标、同一组约束和同一套事实，这才是我真正关心的问题。

所以我现在的开发工作流，核心已经从“怎么让 AI 写代码”逐渐转向另一件事：

**把开发过程中的事实、决策、边界和执行条件显式化，让 AI 的自主执行建立在一组可以检查的状态上。**

整套流程可以先压缩成这一条主线：

```text
证据调查
→ 决策门禁
→ 规格门禁
→ 复杂度门禁
→ 快速补丁 / 实施计划 / 测试方案
→ Coding / Test Agent 执行
→ 新证据回流
```

这里最重要的并不是每一个步骤本身，而是步骤之间的约束关系。

上一步没有满足条件，下一个阶段就不能假装条件已经成立。

---

## 一、我真正想控制的是 AI 的“执行半径”

传统开发流程里，人天然承担了大量隐式判断。

开发者看到一个 Bug，会结合项目历史、模块职责、既有接口、团队习惯和业务背景，很快过滤掉一些不合理的方案。很多判断甚至不会被写下来。

AI 没有这些默认上下文。

如果只给它一句：

> “支付状态偶尔不对，查一下然后修了。”

模型需要自己补全很多东西：

- 当前现象是不是线上缺陷；
- 预期行为有没有被明确过；
- 状态由前端、后端还是第三方支付回调负责；
- 数据库里的字段是最终事实源，还是缓存结果；
- 修复是否允许改变接口返回；
- 当前问题能不能局部处理；
- 需要补什么测试；
- 修改过程中发现新问题以后，要不要顺手一起修。

这些问题里，有些属于实现细节，可以授权给 AI；有些已经触及产品语义、系统职责或外部协议，不能让模型自己选一个“看起来合理”的答案继续执行。

因此我没有试图给 AI 写一个越来越长的万能 Prompt。

我选择把这些判断拆成一组明确的门禁（Gate）。

所谓门禁，就是：**进入下一阶段之前，必须满足一组可验证的前置条件。**

这样 AI 的自主能力依然可以很强，但执行半径受到状态约束。

## 二、第一层：证据链必须先于解决方案

这套流程的起点始终是证据。

这里的“证据”并不等于把仓库扫一遍，也不等于让模型总结大量代码。目标是建立一条足以解释当前问题的最小链路。

以一个线上状态异常为例，我通常希望调查能够回答：

```text
触发条件
→ 入口
→ 核心调用链
→ 状态 / 数据从哪里产生
→ 谁消费它
→ 是否经过持久化或外部系统
→ 失败发生在哪里
→ 最终为什么表现成用户看到的现象
```

调查过程中，所有结论还需要区分真实性等级。

我现在至少会区分四类：

- **已验证事实**：源码、日志、测试、配置或运行结果能够直接证明；
- **推断**：依据现有链路推出来，但还没有直接证据；
- **假设**：可能成立，需要进一步验证；
- **未知**：当前材料无法回答。

这个区分看起来很基础，但对 AI 特别重要。

模型很擅长把“合理推断”写得像“已经确认”。一旦这种信息进入后续计划，它很容易被下游 Agent 当成事实继续消费。

所以我的要求是：**事实和假设不能混在同一种语气里。**

### Bug 也需要先分类

用户说“这是 Bug”，在工作流里仍然只是一个输入。

调查阶段需要先判断问题到底属于什么类型，例如：

- 真实的生产缺陷；
- 当前能力根本没有实现；
- 产品或系统行为尚未决定；
- 测试本身有问题；
- 测试环境或 Harness 有问题；
- 文档和代码已经漂移；
- 技术债或维护性问题；
- 证据不足。

这一步会直接决定后面的路由。

“功能没实现”和“线上回归缺陷”都可能表现为“点了没反应”，但前者可能需要先确认需求，后者才适合进入根因调查和修复。

如果这里分错，后面的代码写得再好也没有意义。

## 三、第二层：决策门禁决定 AI 在哪里必须停

调查得到事实以后，下一步也不一定是编码。

我给 AI 划了一条决策权限边界。

普通实现细节可以自主处理，例如：

- 局部函数怎么拆；
- 变量和私有方法怎么命名；
- 已确定行为下的条件判断怎么组织；
- 在既有架构内选择合适的实现位置。

但当问题开始影响系统语义，我要求流程进入“需要决策”的状态。

典型情况包括：

- 模块或服务职责发生变化；
- 状态由谁拥有、谁推进；
- 数据模型或迁移方式；
- 外部 API、RPC、事件、Schema 或错误语义；
- 同步与异步边界；
- 用户可见行为、失败方式和恢复方式；
- 外部系统接入；
- 权限、安全、审计；
- 重要的并发、幂等和生命周期设计。

这些问题往往没有单纯由源码决定的唯一答案。

源码可以告诉 AI 当前系统怎么做，也可以帮助分析修改成本，但“以后应该怎么做”已经进入产品或架构决策。

因此一旦触发这类问题，流程需要明确标记：

```text
DECISION_REQUIRED
```

随后进入正式讨论。

讨论的产物也有结构要求：

```text
当前事实
→ 冲突或缺口
→ 可选方案
→ 各方案的影响
→ 用户决策
→ 决策边界
→ 尚未解决的问题
```

这里有一个我很看重的原则：

**AI 可以把决策所需的信息准备得非常充分，但不能悄悄把高影响决策埋进实现细节里。**

## 四、第三层：规格门禁负责把决策变成下游可消费的事实

只完成讨论还不够。

长链路 AI 开发经常会经历多个上下文：负责调查的模型、负责规划的模型、真正写代码的 Coding Agent、负责验证的 Test Agent。

如果关键决定只存在于聊天上下文里，后面的 Agent 很容易重新解释。

所以我增加了 Spec Gate，也就是“规格门禁”。

它要解决的问题很直接：

> 当前任务是否已经拥有一份足够稳定的目标行为，能够被后续步骤直接消费？

规格门禁有三种结果：

```text
required
→ 需要正式冻结结论

not_required
→ 影响很小，不需要单独规格，但必须记录为什么可以跳过

undetermined
→ 信息还不够，返回调查或讨论
```

例如，我们已经决定：

> 支付订单的最终状态只由服务端根据支付平台事件推进，客户端查询接口只读取状态，不拥有最终状态写入权。

这句话一旦进入正式结论，后面的实施计划、代码和测试都必须继承它。

这里就涉及整套流程里另一个关键概念：**状态继承（State Inheritance）**。

下游阶段消费上游已经确认的状态，不能无条件重新推导。

如果 Coding Agent 在实现时发现新证据，证明原来的结论有问题，它应该把流程退回相应阶段；如果没有新证据，就继续执行已有结论。

这解决了一个很常见的问题：

同一个需求在分析阶段已经讨论清楚，到了编码阶段模型又重新做一次产品设计，到了测试阶段测试模型再定义一套自己的“正确行为”。

我希望每个阶段可以补充事实，但不能随意重置上游已经冻结的语义。

## 五、第四层：复杂度看传播半径，不看代码行数

规格清楚以后，我还不会立即决定是否直接改代码。

接下来要判断的是修改的传播半径。

我现在把任务粗略分成 S / M / L 三档。

这个分类主要看修改会传播多远，而不是代码量。

### S：局部、低传播

典型特征：

- 根因已经明确；
- 修改点清晰；
- 影响局限在局部；
- 不改变数据模型；
- 不改变公开接口或事件协议；
- 不调整模块职责；
- 不涉及复杂状态机、并发、幂等或生命周期；
- 回归验证边界明确。

### M：跨文件或跨层，但边界仍然清楚

例如：

- 接口层、业务层和测试需要一起调整；
- 一个行为需要沿调用链传播到多个文件；
- 需要明确若干任务之间的依赖顺序。

### L：高传播、高风险

通常包括：

- 跨模块或跨服务；
- 数据迁移；
- 状态机；
- 并发、幂等和复杂生命周期；
- 外部协议变化；
- 安全和权限；
- 新基础设施或外部系统；
- 复杂的失败恢复。

这个判断非常重要，因为它直接决定执行路径。

```text
S + 满足快速通道条件
→ 可以直接 Patch

M / L
→ 先形成实施计划
→ 再交给下游 Coding Agent
```

三行代码也可能是 L。

例如只改一个字段的含义，却同时影响 API、数据库、事件消费者和历史数据兼容，那么它的传播半径已经远远超过一个“小修改”。

## 六、Patch Fast Lane：什么情况下 AI 可以直接改生产代码

为了避免流程过重，我保留了一个小补丁快速通道（Patch Fast Lane）。

这是当前工作流里唯一允许直接修改生产代码的受控路径。

进入快速通道需要同时满足一组条件：

- 根因已经确认；
- 目标行为已经确认；
- 没有待处理的高影响决策；
- 不改变模块或服务职责；
- 不改变状态所有权；
- 不改变同步 / 异步边界；
- 不改数据模型或迁移；
- 不改公开 API、RPC、事件、Schema 或错误合同；
- 不引入复杂状态机、并发、幂等和生命周期；
- 修改点和影响范围可以从当前源码证据中明确界定；
- Patch 能够被局部验证和回放。

只要其中任何一项不满足，就不能因为用户说“直接改吧”而绕过门禁。

路由规则大致是：

```text
根因未知
→ 返回调查

存在高影响未决问题
→ 返回讨论 / Spec

范围已经达到 M / L
→ 生成实施计划

确认是 S 且所有 Fast Lane 条件成立
→ 直接 Patch
```

快速通道还有一个运行时退出条件：

**如果真正修改时发现传播范围超过原先判断，立即停止继续扩散修改。**

例如最初以为只是一个空值判断，追下去却发现真正原因是两个服务对状态含义理解不同，这时任务已经自动失去 Fast Lane 资格。

这个设计的重点是让“直接修”成为一种受控能力，而不是一句 Prompt 带来的无限授权。

## 七、M / L 任务里，实施计划本身就是 Agent 的执行合同

范围达到 M 或 L 以后，我不会直接让 Coding Agent 自由探索整个仓库。

上游会先生成一份足够具体的实施计划。

这里的“计划”也不等于传统项目管理里的任务清单。

它更接近一份给执行 Agent 使用的工程合同。

一份合格的计划至少需要包含：

- 当前源码事实；
- 已确认的目标行为；
- 修改的传播路径；
- 涉及的文件和符号；
- 修改前必须阅读的代码；
- 每个任务允许修改的范围；
- 明确禁止顺手处理的范围；
- 任务依赖关系；
- 停止条件；
- 预期 Diff 形态；
- 行为用例；
- 验证方式；
- 验收标准。

我后来越来越重视 `Read Before Edit`、`Write Set` 和 `Stop Conditions` 这三个东西。

### Read Before Edit

告诉 Agent：动这个任务之前，哪些实现、接口、测试必须先读。

### Write Set

限制这个任务允许修改哪些文件或模块。

### Stop Conditions

一旦发现哪些新情况必须停下来，不能自己扩大任务。

有了这些约束以后，计划才真正能降低 Agent 执行过程中的自由度漂移。

### 默认使用 TDD

对于能够自动测试的生产代码任务，我现在默认要求：

```text
Red
→ Green
→ Refactor
→ Regression
```

先通过失败测试证明问题能够被观测，再做最小实现让测试通过，随后整理代码，最后执行回归。

这里还有一个细节：

如果测试因为环境坏了而失败，这不能算 Red。

如果你新写的回归测试一开始就是 Green，也要先检查测试是否真的覆盖了缺陷。

这些规则的目的，是防止“测试存在”被误当成“缺陷已经被证明并修复”。

## 八、业务测试和技术测试要分开设计

我最初也习惯把测试方案写成一大份文档。

后来发现这里其实存在两个不同问题：

### 业务测试回答：系统应该表现成什么样

它关注：

- 用户目标；
- 预期行为；
- 当前行为和目标行为的差异；
- 功能清单；
- 状态组合；
- 跨对象约束；
- 业务场景；
- 可以验收的结果。

### 技术测试回答：怎样可靠证明这些行为成立

它关注：

- 应该在哪一层测试；
- 可以复用哪些现有测试资产；
- 需要什么 Harness；
- Fixture 如何准备；
- 环境如何初始化和重置；
- 哪些故障需要注入；
- 怎样区分 Fresh Run 和历史结果；
- 怎样处理 Flaky Test；
- 最终需要保存哪些执行证据。

把这两件事拆开以后，一个明显的好处是：

业务测试不会为了“可测”偷偷改变产品预期；技术测试也不会在没有业务依据时自己发明正确行为。

两者都必须消费同一份上游规格。

如果是高传播任务，却没有有效结论，测试方案本身应该被判定为不完整。

## 九、工作流真正重要的地方：状态可以继承，也可以被新证据推翻

把上面的流程放在一起以后，它实际上形成了一个受约束的状态机。

```text
调查中
→ 根因确认 / 目标明确
→ 可能需要决策
→ 规格已冻结
→ 复杂度已确认
→ 可直接 Patch 或进入计划
→ 执行
→ 验证
→ 新证据
```

这里有两个方向都很重要。

### 向下：状态继承

已经确认的事实和决策会继续向下游传播。

下游不用每次重新猜：

- 根因是什么；
- 目标行为是什么；
- 哪些方案已经被排除；
- 哪些边界不能改变。

### 向上：证据回流

流程也不是单向流水线。

Coding Agent 可能发现之前没有看到的调用链。

Test Agent 可能证明某个假设不成立。

这时新证据可以使上游状态失效，任务重新回到调查、讨论或规格阶段。

所以我更愿意把这套流程理解成：

**证据驱动、状态可继承、必要时可回退的工程闭环。**

## 十、主任务之外发现 Bug，不能让整个上下文被带跑

还有一个实际使用中非常容易遇到的问题。

AI 在做调研、讨论或规划时，经常会顺手发现另一个真实 Bug。

如果直接追这个新问题，原任务会被打断；如果完全忽略，又很可能以后找不到。

所以我给这类情况单独做了旁路处理。

规则大致是：

1. 先确认它确实是独立的生产缺陷；
2. 冻结最小证据；
3. 检查是否已有 Issue；
4. 同根因的开放 Issue 追加证据；
5. 同根因已关闭但确实复发，重开；
6. 根因不同才新建；
7. 完成记录后，回到原来的主任务。

这里我刻意不允许“发现了就顺手修”。

因为一个旁路问题没有经过当前主任务的调查和门禁，自动修复会重新打开一条未经控制的执行路径。

## 十一、GitHub Issue 在这里更像一个外部状态存储

我的流程里会出现：

- 【调研】
- 【讨论】
- 【结论】
- 【实施计划】
- 【技术测试方案】
- 【业务测试方案】
- 【缺陷】

看起来像是一套 Issue 命名规范，但我实际使用时更看重另一层价值。

这些 Issue 相当于把长链路任务里的关键状态从模型上下文中拿出来，放进一个可持续读取的外部存储。

模型上下文会变。

Agent 会换。

一次聊天会结束。

但经过冻结的调查事实、用户决策、规格、计划和测试边界仍然可以被后续阶段重新读取。

这也是为什么我不希望每一个 Agent 都从一句原始需求重新开始。

如果上游已经花了大量成本确定根因和边界，下游最有价值的工作是消费这些状态并继续推进。

## 十二、最后，这套流程解决的到底是什么问题

如果只看表面，这套系统包含很多 Skill、很多 Issue 类型和一些 Gate。

但我现在更愿意把它归结为三个工程问题。

### 1. 降低隐藏假设

尽量把“大家默认都知道”的信息变成显式事实、决策和边界。

### 2. 控制自主执行半径

AI 可以在条件满足时高速执行；触碰产品语义、系统职责、数据合同和高传播修改时自动收缩权限。

### 3. 保持长链路一致性

让调查、讨论、规划、编码、测试之间共享同一组已确认状态，减少每个阶段重新解释需求。

AI 能力越强，我越觉得这个问题会越重要。

模型能力继续提升以后，我们大概率会愿意给它更大的自主权。真正决定自主权能不能安全扩大的关键，并不只在模型本身。

还取决于外围系统有没有能力告诉它：

```text
你现在知道什么；
哪些只是猜测；
哪些决定已经确认；
哪些决定你没有权限做；
你当前允许修改多大范围；
什么时候必须停止；
什么证据才算完成。
```

当这些东西足够清楚以后，AI 的执行能力才能真正变成工程能力。

## 附：当前流程和内部 Skill 的对应关系

正文里我尽量使用工程概念，不要求读者先理解内部 Skill 名称。当前实现大致对应如下：

| 阶段 | 主要职责 | 当前 Skill |
|---|---|---|
| 源码 / 能力调查 | 建立真实调用链和当前能力边界 | `github-research-document-generator` |
| Bug 调查 | 分类问题、确认根因或假设 | `github-bug-investigation` |
| 讨论 | 处理需要用户决定的高影响问题 | `github-discussion-facilitator` |
| 规格冻结 | 形成下游可消费的目标行为 | `github-spec` |
| 小补丁 | S 级、低传播修改的受控实现 | `source-patch-implementation` |
| 实施计划 | 把 M / L 任务转成可执行 Agent 合同 | `github-development-plan-generator` |
| 技术测试方案 | 设计如何可靠证明行为成立 | `github-technical-test-plan-generator` |
| 业务测试方案 | 定义业务行为和验收场景 | `github-business-test-plan-generator` |
| 测试方案审计 | 检查测试方案本身是否完整、可执行 | `github-test-plan-audit` |
| 旁路 Bug 记录 | 主任务中发现独立缺陷时留痕 | `github-incidental-bug-capture` |

这张表更适合当作实现索引。整套系统真正需要记住的仍然是前面的状态流：

```text
Evidence
→ Decision Gate
→ Spec Gate
→ Complexity Gate
→ Execution
→ Verification
→ Evidence Feedback
```

后续如果继续演进这套流程，我会优先继续收紧每个状态的输入和输出，而不是单纯增加更多 Skill。
